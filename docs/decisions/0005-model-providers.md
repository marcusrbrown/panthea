# 0005: Model providers

## Status

Accepted (2026-09-27). Confirmed by the M0 inference-baseline and provider-matrix probes: a local baseline model profile, the hosted arm and fallback chain, and the offline-silence proof are all measured below. The shared heavy-work memory policy (coexistence probe) is **not** part of this ADR's Accepted gate and remains open — see Decision.

## Context

D02 requires full offline capability with optional hosted models; D22 requires a configured fallback sequence with no silent hosted fallback in offline mode; P06/P07 require guided local setup, role-based model assignment, and optional mixed local/hosted providers with measured fallback behavior.

## Decision

Local serving, confirmed: **Ollama 0.34.4** (native `/api/chat`, `options.num_ctx` for per-request context size, `format` for JSON-Schema-constrained output, tool calling). Baseline model profile, measured against 8 candidates × 2 context tiers × 40 prompts each ([tools/probes/inference-baseline/README.md](../../tools/probes/inference-baseline/README.md)): **`llama3.2:3b`, 4K context, `parallel=1`** — native schema validity 100%, kind-acceptable 83%, TTFT p50/p95 155/210 ms, completion p50/p95 706/1538 ms, server RSS 2783 MiB. `gemma4:e4b` is the quality runner-up (kind-acceptable 93% at 1K context, completion p95 3600 ms) but is not the default: population-scale cadence is latency-bound once a candidate clears roughly a 70% kind-acceptable bar, and gemma4:e4b's latency is several times higher for a smaller accuracy gain. `llama-server` (llama.cpp) is confirmed as a viable alternate server on the identical GGUF — close parity at 4K (83% kind-acceptable both servers; completion p95 1363 ms on llama-server vs 1538 ms on Ollama) — if Ollama's own concurrency or schema handling regresses. `parallel=2` on Ollama measured **worse** wall-clock throughput than `parallel=1` (1.05 vs 1.24 req/s) at roughly double the RSS (4728 vs 2780 MiB), confirming `parallel=1` rather than merely assuming it.

Reasoning-turn schedule and population allocation: at this baseline profile's measured p95 (1538 ms), a single bounded queue (concurrency 1) supports **~39.0 reasoning turns/minute** system-wide. Spread flat round-robin across 27 characters (7 gods + 20 inhabitants), that cadence is already below the 30 s per-character acceptance-plan starvation threshold — a flat round-robin is not viable at full population, confirming the concern `open-decisions.md` flagged for the M0/M2 probes. The scheduling policy this ADR settles for M2+ is **gods-first, inhabitants-on-routines**: the 7 named gods hold priority access to live reasoning turns (their cadence must clear the 30 s p95 acceptance target); the 20 ordinary inhabitants run primarily on routine/heuristic behavior (the same pattern defaults.md already uses for absent-player mortals, and the background-scheduling capability W06 already requires) with reasoning turns granted from whatever queue budget remains, not on a flat per-character round-robin. This tunes cadence under D23 delegated authority; it does not reduce the seven-god content roster or remove inhabitant participation — defaults.md explicitly forbids hiding an inference bottleneck by cutting content, and this policy is the alternative to that.

Hosted, confirmed: the arm is **OpenCode Go** ([tools/probes/provider-matrix/README.md](../../tools/probes/provider-matrix/README.md)). Its free models (`space-bunny-free`, `longcat-2.5-preview-free`) are reachable over `/chat/completions` with the `opencode-go` credential, both producing valid structured actions (via the repair pass, see caveat below) and supporting tool calls this run — measured latency p50 ~5.0 s and ~19 s respectively (longcat markedly slower). The confirmed order is Go's free models first, then its paid model (`mimo-v2.5`) as the in-Go fallback. **OpenCode Zen is a scope note, not a usable arm for M0**: its `zen/v1` free tier returned a typed 403 `FreeTierError` on every tested request (2/2 this run; 23/23 in a dedicated prior sweep across headers/endpoint/key-source combinations, plus a targeted follow-up for a reported request-shape heuristic that also didn't reproduce it) from what the error itself identifies as a non-public inference service. Zen and Go share the identical underlying credential (`opencode`/`opencode-go` auth.json entries hold the same key, confirmed by direct comparison) — this is a deliberate provider-side scope gate, not a missing key or a subscription-tier difference. Configured fallback sequence, confirmed working: Go free → Go paid → local Ollama → routine-only. OpenAI/Anthropic remain contract-tested only (no keys, per plan scope): the shared `repair.ts` pass produces an identical parsed action across both adapters' fixture shapes, and a no-valid-action fixture fails identically across both.

**2026-09-28, hosted adapter (owner decision):** the OpenCode Go adapter is opt-in and never used offline (D22). It reads credentials only from the macOS Keychain. Paid Go models may join the fallback chain when the operator explicitly configures them. Production does not reuse the provider-matrix probe's `auth.ts` (which reads OpenCode's JSON credential file, `~/.local/share/opencode/auth.json`), its default step order (Go free, Go paid, local Ollama, then routine-only, so hosted before local) or its flat 25 ms retry backoff (`DEFAULT_STEP_ORDER` and `RETRY_BACKOFF_MS` in `tools/probes/provider-matrix/src/fallback.ts`); those are probe conveniences. The fallback order measured above is the probe's, and production routing follows the operator's configuration.

**2026-09-29, correction (owner):** the provider model is simpler than the 2026-09-28 note made it. A provider is any OpenAI-compatible endpoint: a base URL, a model, and an optional key. Local Ollama is one; OpenCode Go (the owner's subscription, an easy way to try a cloud provider) is another; any other compatible endpoint works the same. This follows the brief, which assigns models by character or agent role and lets local and hosted providers mix ([brief.md](../product/brief.md), [technical-constraints.md](../product/technical-constraints.md)). There are no tiers: any role can use any configured endpoint, and the fallback sequence (D22) is an operator-ordered list over the same endpoints, with no local-first or hosted-first rule and no paid or free gate. Two rules distinguish endpoints, and both are repo invariants: offline mode drops non-local endpoints from assignment and fallback before any adapter is built (D02, D22), and a key lives only in platform credential storage (the macOS Keychain) and stays out of config, prompts, saves, trace, and logs (AGENTS.md). The 2026-09-28 note's "opt-in" therefore means "used only when configured, like any provider", and its paid-Go gate is withdrawn: the operator's configuration is the only gate. M0's measurements (Go models at 0% native schema validity, so repair is required; latency p50 about 5 s and 19 s) are evidence about today's Go models, not a reason to restrict the provider. M2 builds one endpoint-generic router and focuses on local models. Go works by configuration: a base URL, a model, and a Keychain key that the shell reads and passes to the sidecar at spawn with the launch token; changing the key restarts the sidecar. M2's evidence runs use local models.

**2026-10-02, correction (owner):** OpenCode Go is not used for Panthea's game or gate traffic. The endpoint model above still holds: any OpenAI-compatible endpoint works by configuration. But Go's usage policy ([Where can I use it?](https://opencode.ai/docs/go/#where-can-i-use-it)) limits it to OpenCode and similar coding-agent traffic, monitored for abuse, and god turns are not that traffic. The router already sends Go's required `x-opencode-session` header and its own user agent, so this is a policy limit, not a wire limit. The provider-settings plan's manual run with a role pointed at Go stays open. Hosted evidence runs will use the owner's self-hosted OpenAI-compatible proxy instead ([hosted endpoint practice](../solutions/best-practices/hosted-endpoint-policy-and-smoke-test-2026-10-02.md)).

Offline proof, confirmed silent on the wire: 20 offline-mode requests produced zero hosted-client constructions in this probe's own fallback router, and a `sudo`-elevated packet capture (all interfaces, including loopback/IPv6/utun/awdl, plus a DNS-query log) observed **zero packets** matching a resolved provider IP or a provider-host DNS lookup. A positive control — one real, non-offline request routed through the identical capture path — measured 39 provider packets, confirming the capture path can see provider traffic and that the offline silence is real, not a blind capture.

Provider abstraction, confirmed with a caveat: Vercel AI SDK 7 (`ai@7.0.93`) with `@ai-sdk/openai-compatible` for Ollama/llama.cpp/OpenCode Go, and `@ai-sdk/openai`/an Anthropic adapter for their native APIs, parameterized by base URL so every server shares one path — this shape held up. The caveat: **no tested Go model produced natively schema-valid output** — every tested response (`space-bunny-free`, `longcat-2.5-preview-free`, `mimo-v2.5`) needed the shared repair pass (`repair.ts`: extract JSON, re-validate) to reach a valid parsed action (native validity 0% across all three, repaired to a valid action in every case that didn't outright fail). The repair path is therefore not an optional resilience feature for hosted models — it is the load-bearing mechanism for every tested Go model; any future hosted provider addition must budget for it rather than assume native JSON-Schema compliance.

**Heavy-work memory policy — superseded by re-measurement, kept for history**: on the 16 GB baseline, an earlier pass read the M0 coexistence probe as settling an **admission-controlled queue** — a new image job starts only when free+inactive memory is ≥ 3 GiB, and only one image job runs at a time — measured against a renderer+LLM-only baseline (LLM p50/p95 611/1535 ms) at LLM p95 **-10.6%** (1373 ms) while completing 7/7 queued image jobs; a global mutex (+1404% LLM p95, 23094 ms) and unconstrained concurrency (+44%, 2216 ms) were both measured worse and rejected; a stricter 5 GiB admission gate starved image generation entirely (0/7 images completed). A follow-up review found the original per-scenario latency sampling mixed successful and failed/timed-out requests with no evaluability floor, so the -10.6% admission-queue figure above is **not trustworthy** and this call does not stand.

**Heavy-work memory policy: NOT decided.** A corrected re-measurement (success-only latencies, an evaluability floor of ≥20 successes and ≤5% error rate) is only directly comparable for the one pair of candidates measured together in the same session: baseline (A) LLM p50/p95 645/1242 ms (60/60 successes) and the 3 GiB admission queue (D@3GiB) LLM p50/p95 1574/3086 ms (60/60 successes, 6 images completed) — a **+148% p95 penalty**, the opposite of the superseded claim above. Unconstrained (B: 1315/2216 ms p50/p95, 7 images completed), the single global mutex (C: 22784/23094 ms, 8 images completed), and the 5 GiB admission gate (D@5GiB: 626/960 ms, 0 images completed) are **first-round, not evaluable — no comparable baseline**: they were measured in a different session than the re-measured baseline, without success/attempt counts recoverable for the evaluability floor, so no percentage change or accept/reject verdict can be assigned to them this round. **Verdict: inconclusive — no candidate policy is supported by the current evidence**; A and D@3GiB are the only evaluable pair, and even that pair rejects the 3 GiB threshold. M1 must re-measure B, C, and D@5GiB together with a corrected baseline before any of them can be closed (accepted or rejected), plus test an admission threshold between 3–5 GiB, rate-limited/backpressured generation instead of a hard admission gate, and scheduling image jobs into LLM idle windows rather than gating on memory alone. LLM inference must never be blocked by an image job regardless of which policy M1 settles on — that constraint holds independent of the open threshold question. See [tools/probes/coexistence/README.md](../../tools/probes/coexistence/README.md) for the full re-measurement; this is the canonical wording, also referenced from [ADR-0003](0003-simulation-service.md) and [ADR-0007](0007-local-image-generation.md).

**2026-09-28, next gate for the heavy-work memory policy:** M1 closed without the re-measurement assigned above, so that assignment no longer stands. The evidence is unchanged. Only the comparable pair counts: baseline (A) against the 3 GiB admission queue (D@3GiB), LLM p95 1242 → 3086 ms with 6 images completed, which does not support the 3 GiB policy. The unconstrained (B), global-mutex (C), and 5 GiB (D@5GiB) candidates have no comparable baseline and no verdict, accept or reject; none is adopted and none is ruled out. The gate: capture the M2 workload baseline (the gods-first schedule running with routines and provider fallback) at M2 exit; before M4 enables concurrent image generation, run each candidate against that baseline and record errors, successes, queue wait, completed images, LLM responsiveness (p50/p95), and memory together for the same session. Results missing any of those are not comparable and cannot close a candidate. Until then continuous character activity comes first: image work uses the accepted temporary/procedural art path ([ADR-0007](0007-local-image-generation.md)) and final artwork waits. Offline local image generation stays in scope, and LLM inference is still never blocked by an image job.

**2026-10-02, M2 local baseline (owner):** the M2 experience gate rerun on qwen3 8B at a 4K context with reasoning off (`tools/scenarios/m2-greek-cast/episodes/2026-10-02T14-29-04/`) was rated continue, and qwen3 8B at 4K (`qwen3-8b-4k`, `tools/probes/inference-baseline/Modelfile.qwen3-8b-4k`) is the local baseline model for M2, with p50 about 6.3 s per request in that run. The `llama3.2:3b` @ 4K profile above is the M0 measurement and stands as recorded; llama3.1 8B (`2026-10-02T14-44-12/`) was run for comparison only.


**2026-10-05, amendment: the per-god starvation target is a queue wait (owner):** the 30 s per-character starvation threshold above is a target for a flat round-robin across 27 characters, and it stays as the history of why the schedule is gods-first. For the seven gods on one local model, the target the gate holds is now a **p95 queue wait of 90 s or less per god** (*the 90 s figure is superseded by the 2026-10-10 amendment below, which sets 105; the rest of this paragraph stands*), where queue wait is the ticks between a god's consecutive requests (a tick is a second of world time; `p95GapTicks` in `tools/scenarios/m2-greek-cast/src/request-timing.ts`, reported per god in each transcript and in the gate summary against the 90 s line). It is amended with the rounds measured in the 2026-10-05 gate (`tools/scenarios/m2-greek-cast/episodes/2026-10-05T14-16-36/`): seven gods on `qwen3-8b-4k` took a turn about every 59 to 76 s (the per-god median gaps of episodes 2 and 3 range 52 to 76 ticks; episode 1's, 63 to 98), with worst gaps of 68 to 108 ticks and 6 to 19 s median latency per request. Episode 1's worst gaps (94 to 108 ticks) were over 90 s, so that episode would not have met the new target; the target is the owner's, and the rated gate reports where it holds. The scheduler's limit of 7 consecutive skips stays as it is. The 2026-10-03 per-god starvation threshold is not removed from the record above: it is superseded as the gate's measure, not erased.

**2026-10-07, M2 local baseline changes to granite3.3 8B (owner):** the owner makes granite3.3 8B at a 4K context, with reasoning off, the M2 local baseline god model, replacing qwen3 8B at 4K. The same rated gate was run on four installed local models. With a prayer open, gods answered directly on 4% of requests (qwen3), 6% (llama3.1), 29% (gemma4) and 84–86% (granite3.3, across two runs); the evidence is in `tools/scenarios/m2-greek-cast/episodes/2026-10-07T14-02-54/`, `2026-10-07T15-44-00/`, `2026-10-07T19-04-46/`, `2026-10-07T18-48-15/` and `2026-10-07T20-12-37/`. granite3.3's latency is comparable (median 7–8 s), every god stayed within the 90 s queue-wait target, and it had the fewest failed checks. The 2026-10-02 qwen3 baseline is superseded and kept as history. Model choice remains an operator setting.

**Amendment (2026-10-10), the per-god queue-wait target is p95 105 ticks (owner):** the 90 s p95 queue-wait target in the 2026-10-05 amendment is superseded; it stays above as the history of the figure. The target the gate holds is now a **p95 queue wait of 105 ticks or less per god** (1 tick = 1 s), measured over service time, which leaves out the outage and catch-up windows as before (`QUEUE_WAIT_TARGET_TICKS` in `tools/scenarios/m2-greek-cast/src/unattended-analysis.ts`).

- **Scope.** Seven gods, `granite3.3-8b-4k` at a 4K context, local Ollama on the owner's machine, and the existing scheduler, where a god that owes something goes ahead of the round. A different model, context, host or scheduler is not covered and needs its own measurement.
- **What was measured.** The third unattended hour (`tools/scenarios/m2-greek-cast/unattended/2026-10-10T12-07-57/`, on `main` at `c74fe32`, Spotlight indexing off) put six gods at a p95 of 93 to 98 ticks (athena 95, hades 93, hephaestus 95, hera 95, hermes 94, poseidon 98) and Zeus at 130. Two Zeus turns skipped by a prompt-cap bug, now being fixed separately, account for the 130; without them his p95 is 97.
- **Why 90 is out of reach.** The mean request took 9.18 s with 9.94 s between picks in the quietest stretch (minutes 13 to 23), and 10.25 s with 11.04 s between picks after the restart. 71 to 80% of rounds after the restart had 8 picks, because a god that owes goes ahead. A p95 of 90 needs a mean request of about 8.6 to 9.2 s. Replays of the run's pick order at the quiet stretch's request times put all seven gods at 90 or under in 3% of trials (median worst god 95).
- **Why 105.** In those replays 105 holds in 97 to 98% of trials at this run's load; 100 holds in only 66 to 87%.
- **Load assumption.** 105 assumes a machine about as quiet as the third hour's (1-minute load 1.5 to 1.9, rising to 2.2 to 3.6). The second hour's heavier load (up to 4.6) would need 110; a run on a loaded machine can miss 105 without the model or the scheduler having changed.
- **Scheduler unchanged.** Strict rotation (`SKIP_CAP` 6) was modelled at 83 to 86, which would meet 90, and the owner kept owed-ahead scheduling instead and moved the target.

The scheduler's limit of 7 consecutive skips and the 300-tick longest-quiet limit are unchanged. The 90 s figure is not erased: it is superseded as the gate's target, and the evidence runs that were judged against it keep that judgment.

## Consequences

**Superseded by measurement (kept for history)**: model quality/latency tradeoffs were probe outputs, not fixed at proposal time — they are fixed now, see Decision above. The AI SDK structured-output concern was real but only partially: native structured output was never observed from a tested Go model, so provider adapters do rely on a hand-rolled repair pass rather than the SDK's native parsing alone — but that repair pass is a designed, shared, tested component (`repair.ts`), not an emergency fallback. Serializing LLM and image work was assumed to bound peak memory at some throughput cost; a global mutex was measured to cap effective throughput far more severely than assumed (+1404% LLM p95, not a mild slowdown) and stays rejected (**2026-09-28:** the mutex figure has no comparable baseline, so it carries no verdict; see the next-gate note in Decision), but the admission-controlled queue's own -10.6% figure did **not** hold up under re-measurement (+148% instead, see Decision) — the memory-sharing policy is open, not settled, and the M4 Pro profile question is downstream of that unresolved threshold.

At 27 characters (7 gods + 20 inhabitants), the measured ~39 turns/minute schedule already exceeds the 30 s starvation threshold under a flat round-robin — addressed by the gods-first/inhabitants-on-routines allocation in Decision above, not by reducing the roster.
